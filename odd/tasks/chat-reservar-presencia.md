Objective: four improvements to the chat found while reviewing it in the browser: the player clears a chat like the owner does, the owner can offer a slot the player books with one click, a connected/disconnected dot, and a "Escribiendo..." indicator.
Branch: feat/chat-reservar-presencia (from feat/agenda-dueno, because the offer is made from the agenda panel) · Delivery: ask-on-risk · Test runner: vitest (`npm test` in apps/server), client: `tsc -b` + eslint (no client test runner)

## Specs

- S1 The player clears a chat the same way as the owner, user words (L1): "noto que cuando el jugador elimina en el chat se borra todo y debe debe tener el mismo comportamiento que como esta programado con el dueño". So for BOTH sides: "deleting" only clears the content (they see only messages after it), the chat stays in their inbox as "Chat vaciado", and the other side keeps everything. This replaces the player half of S4 of `chat-por-reserva.md`.
- S2 Offer with a "Reservar" button, user words (L1): "cuado el dueño despliega la agenda que esta perfecto como se ve, al llegarle el msj al jugador estaria muy bueno que el msj con la fecha y el horario disponibles aparezca con un boton de reservar y redirija a poder abonar y si se abona que quede agendado en la agenda del dueño como cuando se reserva o se paga por completo en "explorar canchas"". So: "Ofrecer este horario" in the agenda panel attaches the slot to the message; the player sees the message with a "Reservar" button that opens the same booking dialog of "Explorar canchas" (seña or total, then Mercado Pago); a paid booking shows in the owner agenda like any other. Assumptions: A1 one offered slot per message and only the owner offers; A2 the server accepts an offer only for a FREE, future slot of the court of that conversation; A3 the button is live: when the slot is no longer free it says so and cannot be pressed; A4 an offer is kept as a snapshot of the time (the slot itself can disappear), without a foreign key, so it never blocks deleting slots.
- S3 Connected dot, user words (L1): "deberia aparecer un punto rojo cuando el jugador y dueño no este conectado y un punto verde cuando el jugador o dueño esten conectados". Each side sees a dot for the OTHER person: green connected, red not connected, in the inbox and in the header of the thread. Assumption A5: "connected" means the app is open in a visible tab (heartbeat every 20 seconds, connected while the last one is under 45 seconds old), not only the chat screen. Assumption A6: presence lives in the server memory (single instance), so a restart shows everybody disconnected for a few seconds.
- S4 Typing, user words (L1): "cuando cualquiera de los dos este escribiendo que aparezca "Escribiendo..."". The other side sees "Escribiendo..." in the thread (and in the inbox row) while the person types, and it disappears about 4 seconds after they stop or when the message is sent. Assumption A7: to feel immediate while an open thread polls, a light "pulse" is read every 2 seconds (connected, typing, last message time) and the full thread is read only when a new message arrived; the typing state is kept in the server memory.
